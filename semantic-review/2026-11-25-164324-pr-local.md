# Supabase client setup and database service layer

`supabase.ts` initializes the Supabase client from Vite env vars. `db.ts` builds on it with mapping functions between app-side camelCase objects and DB snake_case rows, plus CRUD and real-time subscription helpers for the `users` and `properties` tables.

**Watch for:** plaintext passwords stored and returned from the database (confirmed); real-time callbacks that re-fetch the full table on every single-row change (confirmed); `updateUser` silently corrupting fields it was never asked to touch (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

`supabase.ts` will crash at module load if either `VITE_SUPABASE_URL` or `VITE_SUPABASE_ANON_KEY` is absent or empty — `createClient` receives `undefined` and throws at runtime rather than at a clear startup check. The `.env.example` omits both vars entirely, so a fresh checkout will fail silently until the app tries to use the client.

`db.ts` stores and retrieves passwords in plaintext through the `users` table. `dbToAppUser` maps the `password` column directly to the returned user object, and `appUserToDb` sends it back on every write. Any query that fetches a user leaks the credential to the caller.

`updateUser` rebuilds the full DB row via `appUserToDb({ username, ...updates })` before writing. Fields the caller didn't supply default to `''` or `'1'` inside `appUserToDb`, so a partial update — say, changing only `bio` — will zero out every other field in the row.

The real-time subscriptions re-fetch the entire table on every change event, regardless of which row changed. For large datasets this is a correctness-neutral but operationally significant issue: it also means the callback will fire with stale data if the full re-fetch races with another concurrent write.

<details>
<summary>Issues (6)</summary>

1. **Plaintext password in DB round-trip** — `appUserToDb` serializes `user.password` to the DB column, and `dbToAppUser` reads it back. Passwords should never be stored in plaintext or returned to the client. Hash on write, never return on read.

2. **`updateUser` overwrites unset fields** — `appUserToDb({ username, ...updates })` fills every missing field with `''` or `'1'` before the `UPDATE`. A caller passing `{ bio: 'new text' }` will clear `email`, `mobile`, `school`, and every other column. Use a selective DB update that only sets the keys present in `updates`.

3. **Silent crash on missing Supabase env vars** — `supabase.ts` passes `undefined` to `createClient` when `VITE_SUPABASE_URL` or `VITE_SUPABASE_ANON_KEY` is not set. Add a startup guard that throws a clear error if either var is falsy, before `createClient` is called.

4. **`VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` absent from `.env.example`** — Any developer who copies `.env.example` to `.env` will get a broken Supabase client with no hint of what's missing. Add both keys to `.env.example`.

5. **Real-time full-table re-fetch on every event** — Both `subscribeToProperties` and `subscribeToUsers` call `getAllProperties()` / `getAllUsers()` inside the change handler, ignoring the payload. This works, but it fetches every row whenever any row changes. For `subscribeToUsers` in particular (admin dashboard), this is a potential performance and data-exposure issue as the user list grows. Use the `payload` argument from the change event to do a targeted update.

6. **`dbToAppUser` return type is `any`** — The function signature returns an inferred structural type but accepts `row: any`. A DB column rename or missing field produces `undefined` values silently at runtime with no TypeScript error. Type the parameter against `DbUser` and add a return-type annotation.

<summary>Details</summary>

### Plaintext password stored and returned

`appUserToDb` maps `user.password` directly to the `password` column, and `dbToAppUser` reads `row.password` back onto the returned object. This means every `getAllUsers()` call, every `getUserByUsername()` call, and every real-time `subscribeToUsers` callback returns the raw password to any JavaScript code that receives the result. If Supabase RLS is not configured to block `SELECT` on that column for the anon key, it also goes over the wire.

Passwords should be hashed (bcrypt, argon2) before storage. The `password` field should never appear in `dbToAppUser`'s return value — authentication should be a separate operation, not a field on the user record that travels through the app.

### `updateUser` partial-update corruption

```ts
export async function updateUser(username: string, updates: any) {
  const dbUpdates = appUserToDb({ username, ...updates });
  // ↑ Every field not in `updates` defaults to '' or '1' inside appUserToDb
  const { error } = await supabase
    .from('users')
    .update(dbUpdates)
    .eq('username', username);
```

`appUserToDb` unconditionally emits every column with an `|| ''` / `|| '1'` fallback. Spreading `updates` only populates the keys the caller supplied; the rest silently become empty strings. The fix is to build the DB update object only from the keys in `updates`, either by filtering `appUserToDb`'s output or by writing a dedicated partial-mapping helper.

### Missing env var guard in `supabase.ts`

```ts
const supabaseUrl = import.meta.env.VITE_SUPABASE_URL as string;
const supabaseKey = import.meta.env.VITE_SUPABASE_ANON_KEY as string;
export const supabase = createClient(supabaseUrl, supabaseKey);
```

The `as string` cast suppresses TypeScript's awareness that the value could be `undefined`. If either var is absent, `createClient` receives `undefined` cast to `string` and will either throw an opaque internal error or produce a client that fails on every request. A two-line guard before `createClient` makes the failure immediate and legible:

```ts
if (!supabaseUrl || !supabaseKey) {
  throw new Error('VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY must be set');
}
```

### Real-time subscription re-fetch strategy

Both subscription functions discard the `payload` from the Postgres change event and re-fetch the whole table:

```ts
.on('postgres_changes', { event: '*', ... }, async () => {
  const properties = await getAllProperties(); // full table scan
  callback(properties);
})
```

For `subscribeToProperties`, this means every insert, update, or delete by any landlord triggers a full `SELECT *` and delivers the entire dataset to the subscriber. For `subscribeToUsers`, this delivers all user records (including, currently, their passwords) to whoever subscribed. The payload contains the changed row's new and old values and is sufficient for most incremental update patterns.
