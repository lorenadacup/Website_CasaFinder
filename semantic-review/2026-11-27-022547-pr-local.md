# CasaFinder runtime correctness bugs

This review covers four files from a React/TypeScript + Supabase property-listing app: `App.tsx`, `db.ts`, `BarangayDrawingTool.tsx`, and `BarangayBoundarySystem.tsx`. The focus is exclusively on correctness — things that break at runtime or produce wrong behavior. No style or best-practice findings.

**Watch for:** Password change accepts any input without verifying the current password (confirmed); `handleSaveProfile` syncs landlord property denormalization to local state but never persists it to Supabase (confirmed); `handleApproveLandlordAccount` reads a stale `propertiesList` closure when firing property approvals (confirmed); a user can bypass the OTP step and reset any password by calling `handleResetForgotPassword` directly (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

The forgot-password flow generates an OTP and shows a verification screen, but `handleResetForgotPassword` has no server-side or in-handler guard on `forgotOtpVerified`. The function only requires `forgotFoundUser` to be non-null, so any user who can set that state — including by typing a known username — could call the reset path. In practice the UI gates on `forgotOtpVerified` in JSX, but nothing in the handler itself enforces it.

The profile settings form renders a "Current Password" field, but `handleSaveProfile` never reads `profileCurrentPassword` and never compares it to the stored password before writing `profileEditPassword` into the user record. Any logged-in user can change their own password without knowing their current one.

When a landlord updates their profile, `handleSaveProfile` reflects the new contact details across all their property listings in React state, but never calls `upsertProperty` for the changed listings. Those denormalized fields (name, mobile, email, bio, avatar, Facebook, permit number) revert on the next full page load from Supabase.

`handleApproveLandlordAccount` and `handleRejectLandlordAccount` both call `propertiesList.filter(...)` directly — referencing the closure value at the time the functions were defined, not the live state. If `propertiesList` changes between renders (e.g., a realtime subscription fires), the Supabase `updatePropertyApproval` calls will operate on the stale snapshot and silently miss properties added after the last render cycle that captured those functions.

<details>
<summary>Issues (5)</summary>

1. **Password change skips current-password check** — `handleSaveProfile` never reads `profileCurrentPassword` or compares it to the stored password. Remove the "Current Password" field, or add `if (profileCurrentPassword !== currentUser.password) { setSecurityErrorMsg(...); return; }` before the update.

2. **Forgot-password OTP bypass** — `handleResetForgotPassword` guards only on `!forgotFoundUser`, not on `forgotOtpVerified`. Add `if (!forgotOtpVerified) return;` at the top of the handler.

3. **Landlord profile update not persisted to Supabase** — After updating `propertiesList` in state to reflect new landlord contact details, the handler never calls `upsertProperty` for the affected listings. Add a `Promise.all(changedProperties.map(p => upsertProperty(p)))` call after the state update.

4. **Stale closure in account approval handlers** — `handleApproveLandlordAccount` and `handleRejectLandlordAccount` capture `propertiesList` at definition time and iterate it directly. Wrap the Supabase property calls to use the updater pattern or read from a ref, or use `setPropertiesList(prev => { prev.filter(...).forEach(...); return prev; })` to access the current list.

5. **Admin-role check rejects by role only, not by account status** — `handleLoginSubmit` correctly prevents non-admins from using the admin login path, but approved admin accounts have no corresponding `accountStatus` check. If an admin account were ever set to `rejected` or `pending` by a DB migration, the app would still let them log in. Add `if (user.accountStatus && user.accountStatus !== 'approved') { setLoginError(...); return; }` for admin logins.

</details>

## Password change without current-password verification

`handleSaveProfile` (around line 1121) validates that `profileEditPassword` and `profileConfirmPassword` match, but never reads `profileCurrentPassword`. The comparison `if (profileConfirmPassword && profileEditPassword !== profileConfirmPassword)` only checks the two new-password fields against each other. The "Current Password" input exists in the JSX (line 5510) and its state is managed, but it is never referenced in the save handler. Any logged-in user can open the Settings tab, type a new password into the "New Password" field, and save — without knowing what the current password is.

Fix: at the start of the `if (profileTab === "settings" && profileEditPassword.trim())` block, add:
```ts
const currentUser = registeredUsers.find(u => u.username === userSession.username);
if (profileCurrentPassword !== currentUser?.password) {
  setSecurityErrorMsg("Current password is incorrect.");
  setIsSavingProfile(false);
  return;
}
```

## Forgot-password OTP bypass

`handleSearchForgotAccount` sets `forgotOtpCode`, sends the OTP email, and sets `forgotOtpSent = true`. The UI then conditionally renders the OTP entry form or the reset form based on `!forgotOtpVerified` (line 2010). But `handleResetForgotPassword` (line 941) only guards:
```ts
if (!forgotFoundUser) return;
```
`forgotOtpVerified` is never checked inside the handler. If the JSX conditional were ever wrong — a React re-render, a component state inconsistency, or a programmatic call — the reset would go through without a verified OTP. Add `if (!forgotOtpVerified) return;` as the first guard after `if (!forgotFoundUser) return;`.

For accounts without an email (line 921: `else { setForgotOtpSent(true); }`), the OTP is generated and stored in state but never sent anywhere — it's visible only in React DevTools. This path offers no real verification.

## Landlord profile denormalization not synced to Supabase

Inside the `setTimeout` in `handleSaveProfile` (around line 1222), when `userSession.role === "landlord"`, the code maps over `propertiesList` and updates each matching property's denormalized landlord fields in React state. It never calls `upsertProperty` for any of those updated property objects. The next time `getAllProperties()` runs (page reload, or when the realtime subscription receives an unrelated update), those listings will show the old landlord name, mobile number, email, bio, avatar, and permit number pulled from Supabase.

The correct fix is to collect the updated properties and persist them:
```ts
const updatedProps = prev.map(...);  // existing logic
updatedProps
  .filter(p => p.landlordUsername === userSession.username)
  .forEach(p => upsertProperty(p).catch(console.error));
setPropertiesList(updatedProps);
```

## Stale `propertiesList` closure in approval handlers

`handleApproveLandlordAccount` and `handleRejectLandlordAccount` are both defined as `const` functions in the component body. Each calls `propertiesList.filter(p => p.landlordUsername === username)` to find the properties to sync. This references the `propertiesList` variable captured at the time React last re-ran the component body — if a Supabase realtime INSERT fires between the last render and the moment an admin clicks Approve, the new property won't be in the closure's snapshot and won't have its `approval_status` updated in Supabase.

The simplest fix is to use a ref that always holds the current list:
```ts
const propertiesRef = useRef(propertiesList);
useEffect(() => { propertiesRef.current = propertiesList; }, [propertiesList]);
// Then in handlers:
propertiesRef.current.filter(p => p.landlordUsername === username)...
```

## Admin login account-status gap

`handleLoginSubmit` for admin users checks `user.role !== "admin"` and blocks non-admins from the admin login path. It does not check `user.accountStatus`. Every other role (student, landlord) is effectively blocked if `accountStatus !== "approved"` by the `isLandlordApproved` guard used to show/hide the Add Listing button — but that guard never affects login itself, and admin accounts have no equivalent post-login block. This is a minor gap today because admin accounts are seeded with `accountStatus: "approved"`, but it is worth confirming the check is intentional.
